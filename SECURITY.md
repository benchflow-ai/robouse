# Security policy

## Reporting a vulnerability

Please do not report security vulnerabilities in public issues, pull requests or Discord.

Report them privately through GitHub's private vulnerability reporting: the **Report a vulnerability** button on the repository's [Security](https://github.com/benchflow-ai/robouse/security) tab. If you cannot use GitHub, email xiangyi@benchflow.ai with "robouse security" in the subject.

Include what you can of the following: the Robo Use version (`robouse --version`), the operating system, the command you ran, what an agent or another process could do that it should not, and the smallest steps that show it. Do not include real credentials; if a report needs one, say where it appeared and how long it was.

We aim to acknowledge a report within 5 working days and to agree on a disclosure date with you, normally no later than 90 days after the report. We credit reporters in the release notes unless they ask us not to.

## Supported versions

Only the latest release on [PyPI](https://pypi.org/project/robouse/) gets security fixes. Robo Use is alpha software; upgrade to the latest version before reporting.

## What to report where

| Problem | Where |
|---|---|
| A credential, token or private file reaches an agent, a model provider, a trial folder, a published page, this repository or a release | Privately, as above |
| An agent can affect something outside its own trial: another trial's episode, the host, a remote simulator worker | Privately, as above |
| A task can be scored without doing it: a judge bug, hidden state printed to the agent, a reference solution reachable by the agent | A public issue with the **Task or scoring integrity** template, unless it also exposes a credential |
| A bug in an upstream simulator, a harness (Claude Code, Codex, Gemini CLI, mini-swe-agent), a model provider or BenchFlow | The upstream project |

## The agent sandbox and its limits

`robouse run` (the local runner) starts every model harness, and the `vla` and `molmoact2` clients, under the operating system's sandbox: Seatbelt (`sandbox-exec`) on macOS and bubblewrap on Linux. The reference solution (`--harness oracle`) and the no-op control run without it. Read this section before you run an agent you do not trust or publish scores.

### What it does

- It denies reads and writes to the trial's run folder, the trial's task folder, any `robouse` source or install (a `robouse` package folder) and, when Robo Use runs from a source checkout, that checkout's `tasks/`, `runs/`, `adapters/` and `assets/` folders.
- It denies `~/.config/robouse`, `~/.config/robouse-operator`, the optional credential pools (`ROBOUSE_CLAUDE_TOKEN_FILE`, `ROBOUSE_CODEX_AUTH_DIR`), the files the episode server loads in later trials when a setting moves them out of Robo Use's cache (robot models in `ROBOUSE_MENAGERIE_ASSETS`, textures in `ROBOUSE_ROBOHARM_TEX`, the chemlab suite's instrument files and behaviour runtimes in `ROBOUSE_CHEMLAB_ASSETS`, the walking policy in `ROBOUSE_HUMANOIDBENCH_POLICY`), so that no trial can change what a later one loads, and every path in `ROBOUSE_SANDBOX_DENY`. For `ROBOUSE_CLAUDE_TOKEN_FILE` it denies that file only, not the folder it is in; list that folder in `ROBOUSE_SANDBOX_DENY` if it holds other secrets.
- It denies credential and task-copy locations in your home folder (`HOME_DENIED` in [`src/robouse/runner/sandbox.py`](src/robouse/runner/sandbox.py)): other programs' logins (such as `~/.ssh`, `~/.aws`, `~/.config/gcloud`, `~/.config/gh`, `~/.netrc` and `~/.docker`), your own Claude Code, Codex, Gemini CLI (`~/.gemini`, and `$GEMINI_CLI_HOME/.gemini` when you set that variable) and mini-swe-agent settings, `~/.env`, BenchFlow's settings and task cache, package caches that hold copies of the tasks (`~/.cache/uv`, pip's cache) and Robo Use's own cache, except the agent's own per-trial harness folder. It also denies a `.env` file in any folder above the trial's run folder, its task folder or the Robo Use install, such as a project's `.env` next to its virtualenv. A denied file is hidden as well as a denied folder.
- Each trial's Claude Code, Codex and Kinex get a config folder of their own, which is removed when the trial ends. The exception is a Codex account pool (`ROBOUSE_CODEX_AUTH_DIR`): Codex then keeps one folder per account, which the trials on that account share. Each trial's Gemini CLI gets a home of its own in the trial's workspace, and does not read the machine's system settings.
- The agent can read but not change the Python that Robo Use runs on, because the episode server and the verifier run on it. The same holds for the Python environment the `kinex` harness shares between trials (`~/.cache/robouse/kinex-venv`), which Kinex's tools and device drivers run in, and for the Kinex install every `kinex` trial runs: the `node_modules` folder its launcher resolves into, with Kinex's packages and the Python helpers its tools and drivers import. Kinex's Python processes keep their bytecode in the trial's workspace (`PYTHONPYCACHEPREFIX`) and ignore `__pycache__` folders next to the sources.
- It denies LIBERO's task data, which gives a LIBERO task's object layout away: the scene files, saved start states and demonstrations (`bddl_files`, `init_files`, `datasets`) of the hf-libero package in the Python Robo Use runs on, and the folders LIBERO's config file names. The episode server and the verifier, which run outside the sandbox, still read them.
- It keeps other trials' workspaces and episode sockets from the agent, and refuses connections to the Docker, Podman and LXD sockets and to your SSH agent.
- On Linux the agent gets its own process namespace, so it cannot see other processes, and its own `/tmp`.
- On macOS it refuses TCP connections to localhost, except to the trial's own model gateway, the `aspire` harnesses' practice broker and the `kinex` harness's device bridge, and the agent cannot start `open`, `osascript`, `shortcuts` or `security` or send Apple events, which act outside the sandbox.
- The runner removes model-provider credentials and settings (`ANTHROPIC_*`, `OPENAI_*`, `CLAUDE_CODE_OAUTH*`, `GLM_*`, `ZAI_*`, `GEMINI_*`, `GOOGLE_API_KEY`, `GOOGLE_GEMINI_*`, `GOOGLE_GENAI_*` and the key variables of every known provider) and every variable whose name marks a credential (a token, key, secret, password or login, such as `GITHUB_TOKEN`, `HF_TOKEN`, `AWS_SECRET_ACCESS_KEY` or `SSH_AUTH_SOCK`) from the agent's environment. Each harness gets back only its own login, or a per-trial key for the trial's model gateway. That key opens only the gateway's model routes (Anthropic Messages, chat completions, Responses and the model list) for the trial's model: LiteLLM's provider pass-through routes (such as `/gemini/...`), which would forward any request to the provider with your key, and its file, batch and other routes are refused. The episode server and the verifier get no model-provider key either.
- The episode server receives the reference solution's token and the key that signs the verdict on its standard input, never in an environment variable or a command line.
- Claude Code is offered only the Bash, Read, Write, Edit, Glob and Grep tools, plus the `robo` MCP tools when it uses them; Codex and Kinex run with their web search turned off; Gemini CLI is offered only its shell, file and search tools, with no web search or fetch, and runs its shell commands without the variables whose names mark a credential, its own `GEMINI_API_KEY` included. That keeps the key out of the commands' environment and output, not out of the agent's reach: Gemini CLI's own process holds it, and an agent can read a process's environment (on Linux from `/proc`, on macOS with `ps`), as it can Claude Code's login.
- The `aspire` harnesses deny the skill library folder (`ROBOUSE_ASPIRE_LIBRARY`): the agent works on a copy in its workspace, and the runner, outside the sandbox, copies the library and the selected program out of the workspace when practice ends and writes back what the trial changed. The copy opens the workspace folder before the agent starts and then each folder and file relative to its parent without following links, checking each on the open file (`O_NOFOLLOW`, `fstat`), so a path the agent swaps for a link at any moment is not followed. Nothing is written back from a trial whose verdict is not a verified result (unsigned, or an integrity failure), and skill files only when the trial's ASPIRE verifier reported the task verified. A task's selected program is reused only by the harness and model that selected it, unless `ROBOUSE_ASPIRE_REUSE=any`.
- The practice broker, which starts the practice episodes, answers only requests that carry the trial's token, never sends a practice episode the reference solution's token, and refuses the scored seed, seeds outside the trial's practice bands and runs past the practice budget. Ending practice (the freeze) takes a second key that only the harness's top process holds. Practice episode sockets are named like other episode sockets, so the sandbox refuses them to every agent.
- The scored episode of an `aspire` trial is locked: it serves only requests that carry a token the runner gives the server and the harness's top process on their standard input, and the agent starts without it. Before the harness's Stage 2 unlocks it, only the runner's status check and give-up are served (with the token: a request's `runner` mark authorizes nothing). After the unlock every request must still carry the token, so an agent process that outlived practice cannot act either. The server counts every request it refused in its signed verdict, and the runner does not score a trial with any refusal, or with steps on an episode that was never unlocked (`IntegrityError`). The harness's top process runs with `python -I`, imports nothing from the agent's workspace, and stops the agent's process group when it is itself stopped. Their Claude Code is also offered the Agent and Skill tools.

### What it does not do

- **It is a deny list, not an allow list.** The macOS profile allows everything by default and denies the paths above. On Linux, bubblewrap binds the whole host file system read-write and hides only the listed paths. Everything else in your home folder and on the machine is readable, and mostly writable, by the agent.
- **Other copies of tasks are readable.** Copies outside the denied places, such as another checkout, a downloaded wheel, an exported dataset or a robohub clone, hold reference solutions and verifiers, and another environment's hf-libero holds LIBERO's scene files and start states. Add such copies to `ROBOUSE_SANDBOX_DENY`, or remove them.
- **The network is open.** The agent can reach the internet through its shell even without web tools. Public copies of the tasks, including reference solutions and verifiers, are downloadable (the [robohub](https://github.com/benchflow-ai/robohub) repository, the package on PyPI, the upstream benchmarks' sources).
- **On Linux, services on this machine are reachable.** There is no network namespace, so the agent can connect to anything listening on localhost.
- **The agent runs as your user** (as root, if you run `robouse` as root). A secret in a variable whose name does not mark a credential reaches the agent, and so does a credential file outside the denied locations unless you list it in `ROBOUSE_SANDBOX_DENY`.
- **Episodes are not authenticated.** The sandbox refuses the agent's connections to other trials' episode sockets, but any process of your user outside the sandbox can connect to a running episode's socket and send it requests. The `kinex` harness's device bridge listens on localhost and answers only requests that carry its trial's session, which only that trial's workspace and environment hold. On macOS, processes of the same user can also read each other's command lines and environments.
- **The lock on an `aspire` trial's scored episode is a token held in memory.** The runner hands the token to the harness's top process on its standard input, which reads it before it starts the agent and keeps it only in memory. A process of your user that can read that process's memory (on Linux, if the ptrace policy allows it) could take it; the agent runs as your user. A request without the token is refused and makes the trial an `IntegrityError`, not a score.
- **An `aspire` program can do what numpy can.** The program contract is ASPIRE's (no imports but `math` and `numpy`, no names or attributes starting with `_`), but numpy itself reads and writes files (`np.load`, `np.fromfile`, `ndarray.tofile`) and reaches memory through `ctypes` (`np.ctypeslib`, `ndarray.ctypes`). Stage 2 runs the frozen program in the harness's top process, inside the sandbox, after the agent has stopped; such a program could read what the sandbox allows, or that process's memory. The contract is ASPIRE's protocol, not a security boundary.
- **The `aspire` library folder is denied to `aspire` agents only.** `ROBOUSE_ASPIRE_LIBRARY` holds each task's selected program. Every harness's agent gets the variable in its environment, and only the `aspire` harnesses deny the folder; an agent of another harness could read the programs there. Keep the folder outside places other trials' agents can read, or list it in `ROBOUSE_SANDBOX_DENY`, when you run other harnesses on the same tasks.
- **Remote simulator workers trust whoever holds their secret.** Robo Use reads a worker endpoints file only from `~/.config/robouse/remote/<name>.json`, which the sandbox denies, or from the file `ROBOUSE_<NAME>_REMOTE` names; keep that file out of every folder an agent can read.
- **An agent can end its own harness.** A harness that exits with an error before the episode ends is recorded as an infrastructure failure (an `AgentError` in `result.json`): the trial is not scored, and `--retries` and `--resume` run it again. The agent runs as your user next to its harness and can end that process from its shell, so an agent about to fail can make its trial unscored. Before you publish scores, look at every trial that ended with an exception and every trial that was retried.
- `ROBOUSE_SANDBOX=0` turns the sandbox off completely.

In short: the sandbox stops an agent from stumbling on the answer, not one that looks for it. For agents you do not trust, use a disposable VM or container with no credentials of yours and no network access except to the model API, or run published datasets with BenchFlow (`bench eval run`), which puts the agent and the simulator in separate containers.

### What we saw in our own runs

Two audits of the leaderboard runs on [robouse.ai/runs](https://robouse.ai/runs/) (September 27 to October 13, 2026) checked every counted solve. Agents in those runs read reference solutions from task copies left in a shared `/tmp`, downloaded upstream benchmark source from GitHub, printed their inherited environment, and connected to other trials' episode sockets. The trials that gained from this were removed from the leaderboard or re-run. The runner has been tightened since then, but the limits above remain, so a score from `robouse run` rests on the trial logs as well as on the sandbox.
